## Implementation Decisions

### Decision 1 — Finalization is a Hook-owned external transition taking only a request target

`StandbyHook.finalizeExercise(uint256 _commitmentId)` matches the conceptual interface in
`implementation-plan.md` §17.2. The parameter is the finalization target the request names and is never
authority: it must equal the commitment the Hook's own causal context is bound to, and the mutation uses
`context.commitmentId` regardless. Every economic fact — `q`, the Beneficiary, the exerciser, the service —
is recovered from the context, so the surface carries no field through which any of them could be
substituted.

### Decision 2 — The router names the commitment its own request was for

`ExerciseRouter.exercise` now carries `_commitmentId` alongside `_maxInput` through the unlock, and
`_finalizeExercise` names that value. The identity check is therefore a real end-to-end check of the
request the caller made against the Hook's causal binding, rather than a tautology built from a value read
back out of the Hook. The payload is decoded after the PoolManager authentication, so a direct caller is
still refused whatever it presents.

### Decision 3 — Finalization happens inside the same PoolManager unlock

The F8C production documentation already stated the intent that finalization would consume the context
inside the same unlock, and the sequence there is load-bearing: nothing may be settled before the execution
is proven, nothing finalized before the Beneficiary has been delivered to. Nothing in `unlockCallback` is
caught, so a refused finalization unwinds the delivery, the settlement, the swap and the authorization with
it.

### Decision 4 — Consumption clears the whole context, and needs no new lifecycle position

`EMPTY` is the consumed position, so `ExerciseAuthorizationState` is unchanged. Consumption writes every
one of the seven context fields back to zero rather than only the position, because a context reporting
`EMPTY` while still carrying bindings would be exactly the reusable evidence consumption exists to destroy.

### Decision 5 — One persistent write, no fulfillment flag, no reference clearing

The only persistent effect is `Remaining -= q`, through the existing `_writeRemainingEntitlement` mechanic.
No `fulfilled` / `completed` / `settled` flag is introduced, no aggregate-obligation decrement is stored,
and the bounded enforcement reference is left in place — completion is `Remaining == 0` and the released
obligation follows from the derivation over the remainder that just changed.

### Decision 6 — An `ExerciseFinalized` event

The one durable Standby economic transition emits observational evidence, as O1 admission does. It exists
because the causal context that attributes a fulfillment is transaction-scoped: what persists afterwards is
a reduced remainder, which does not say which exercise, exerciser, or delivery discharged it. Nothing
enforces against the event.

### Decision 7 — The harness router hierarchy was split rather than repurposed

Production now finalizes, so `UnfinalizedExerciseRouter` — which previously only lifted the completion
barrier — would have started finalizing and would have invalidated the F8C evidence that settlement and
delivery fulfil nothing. It was rebased on a new `NonFinalizingExerciseRouter` (production minus the
finalization request, barrier intact), and the F8C `ProductionExerciseCompletionTest` was pointed at that
router so the production completion barrier keeps a failing case to be verified against. No F8C assertion
was weakened or removed.

### Decision 8 — Environment: the pinned HookMiner needs more than Foundry's default gas limit

Discovered while running the full suite: `test/integration/DeterministicEconomicFixture.t.sol` began failing
in `setUp` with `MemoryOOG` inside `HookMiner.find`. The pinned miner rehashes the whole Hook creation code
and allocates a fresh buffer on each of its `MAX_LOOP` = 160,444 candidate salts, so its cost is quadratic
in the iteration count and Foundry's default `1073741824` call gas limit stops the search after roughly
125,000 of its own iterations. Which salt is valid changes with every edit to the Hook, so under the default
limit any Solidity change can make an unrelated fixture fail to deploy its Hook for want of gas rather than
for want of a salt. Confirmed by re-running the same suite unchanged under `--gas-limit 20000000000`, where
all 15 tests pass.

`gas_limit = 10000000000` was added to both `foundry.toml` profiles and recorded in `docs/setup.md`. It is a
local Foundry execution budget used by Forge tests and local script simulation — not a compiler, bytecode,
EVM-target, optimizer, dependency, deployed-contract, protocol, or deployed-chain gas-limit change — and
Standby's own bounded execution is enforced by explicit protocol bounds and reverts
(`MAX_PROSPECTIVE_SWAP_STEPS`, `MAX_LIVE_COMMITMENTS`) rather than by exhausting a gas limit, so it weakens
no verification.

> Wording correction, recorded as Prompt 1 above: this decision originally described the setting as a
> "test-execution budget only", which was too narrow. The configuration was independently reviewed and
> accepted and its value did not change; only its description was corrected.
